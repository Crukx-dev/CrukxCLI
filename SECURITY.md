# Security policy — CrukxCLI

This repo is the public CLI shell: command entry points
(`crukx-cli`), the session TUI (`crukx-tui`), and git glue
(`crukx-git`). It's built against a private engine crate
([`crukx-core`](https://github.com/Crukx-dev/crukx-core) — reliability
gating, storage, process spawning) that most of the actual attack
surface described below runs through, even though you'd trigger it
from commands defined here.

`crukx` runs entirely on the machine invoking it. No account, no
telemetry, no network calls of its own — every command in this repo
(`run`, `capture`, `replay`, `gate`, `review`, `verify-session`,
`history`) reads and writes only `.crukx/` and the commands you
configure it to run. There's no upload-to-`crukx-cloud` path wired
into the CLI today.

## Reporting a vulnerability

Open a private security advisory on this repo (Security tab →
"Report a vulnerability") rather than a public issue. Include repro
steps and, ideally, a minimal `crukx.yml` / contract JSON that
triggers it. A report that touches the engine gets forwarded to
`crukx-core`'s maintainers; you don't need to know which repo actually
owns the fix.

## Threat model

`crukx gate`/`crukx replay` execute real commands and real
user-authored assertion JS (`assert.mjs`) with full access to the
invoking user's host, by design — that's the product, not a bug (see
"Known limitations" below). The security boundary this CLI actually
tries to hold is narrower:

- A `crukx.yml` or `.crukx/contracts/*.json` you didn't author
  yourself (checked in by someone else, or generated by a CI step you
  don't control) should not be able to make `crukx` read, write, or
  execute a file **outside** the `.crukx/` directories it declares —
  even though the commands it's configured to *run* still get full
  host access once permitted to run at all.
- A contract or session id (`crukx replay <id>`, `verify-session
  <id>`) — plain identifiers, no reason to ever contain a path
  separator — should not be usable to point Crukx at an arbitrary
  filesystem path.

## What we've checked and fixed

A 2026-08-27 review found every join point matching the second bullet
above (contract ids, session ids, a contract's own `assertion_file`
field) built a path by string-interpolating the untrusted value
straight into `PathBuf::join`, with no check that it stayed a plain
filename. Fixed upstream in `crukx-core::security::is_safe_path_segment`
— every one of those call sites now refuses a value containing `../`,
a path separator, or an absolute path, instead of joining it. Full
writeup: [`crukx-core`'s SECURITY.md](https://github.com/Crukx-dev/crukx-core/blob/main/SECURITY.md#what-weve-checked-and-fixed).

## Known limitations (by design, not bugs)

- **No sandboxing of the commands you configure Crukx to run.**
  `crukx run -- <cmd>`, replayed shell steps, and assertion files all
  execute with the invoking user's full host access. Crukx's
  `ExecutionPolicy` refuses actions it can classify as unsafe for the
  configured policy (e.g. a `file_write` under `ReadOnly`) — it is not
  process-level confinement. Don't point `crukx.yml` at a contract or
  assertion file you don't trust, for the same reason you wouldn't run
  an untrusted shell script.
- **Tamper-evidence, not tamper-proofing.** `crukx verify-session`
  detects a session's event log or hash chain being edited
  independently of the other — it can't detect a fully coordinated
  rewrite by someone with write access to both files. There's no
  external signing key or remote anchor in v1.
## Supported versions

Pre-1.0 (`0.1.0-alpha.x`) — security fixes land on `main`; no backport
policy until a 1.0 tag exists.
